Despliegue de SecureVault

Resumen ejecutivo

Para que el docente consulte las notas de prueba por HTTPS, proponemos Render Free para la aplicación y MongoDB Atlas Free para los datos. Ambos cuestan USD 0 dentro de sus cuotas. El enlace seguiría disponible después de días sin visitas, con una espera de cerca de un minuto mientras Render reactiva la aplicación. [3, 12, 13]

1. PaaS, contenedores y VPS

PaaS. El proveedor opera el sistema y supervisa el proceso. El equipo despliega con menos trabajo, a cambio de aceptar límites de configuración. Se paga por instancias, almacenamiento y tráfico. [1, 3, 5]

Contenedor. La imagen fija Node.js y sus dependencias, lo que facilita reproducir el entorno. El equipo controla y actualiza esa imagen. El contenedor puede ejecutarse en un PaaS o en un VPS. El alojamiento y el registro de imágenes determinan el costo. [2, 19]

VPS/IaaS. El equipo controla el sistema operativo, la red y el proxy, y asume parches, copias y recuperación. Se pagan la máquina virtual, el disco y, según el plan, la transferencia. [1]

Arquitectura y operación

Elección para la evaluación. Ubicaríamos la aplicación en Virginia y Atlas Free en AWS Norte de Virginia. Sus 512 MB bastarían para notas de prueba. Atlas evita el vencimiento de PostgreSQL Free en Render y el límite de cinco horas de Koyeb. Heroku Basic eliminaría la espera inicial, pero exige la aprobación previa del crédito para cubrir el costo. [3, 4, 7, 9, 10, 12, 31]

3. Variables de entorno y secretos

NODE_ENV configura el entorno. Un archivo .env local guarda valores legibles y debe excluirse de Git. Una copia expone los secretos. Un gestor restringe su lectura y facilita la rotación y la auditoría. [14, 15]

En el panel de Render guardaríamos DATA_ENCRYPTION_KEY (32 bytes aleatorios), MONGODB_URI y SESSION_SECRET. Node.js los leería al iniciar. El repositorio documentaría solo sus nombres. Para notas y perfil usaríamos AES-256-GCM con IV único, etiqueta y versión de llave. Al rotarla, se escribiría con la nueva y se conservaría la anterior hasta recifrar los datos. Perder la llave y su respaldo haría irrecuperables las notas que la usan. [14, 15]

4. Certificados TLS, Let’s Encrypt y HSTS

El certificado vincula un dominio con su clave pública. El navegador valida nombre, vigencia y cadena de confianza. Let’s Encrypt comprueba el control del dominio mediante ACME y automatiza emisión y renovación. Render gestionaría el certificado y redirigiría HTTP a HTTPS. Al recibir Strict-Transport-Security por HTTPS, el navegador usará HTTPS en visitas posteriores durante max-age. [3, 16, 17, 19]

5. Proxy inverso y trust proxy en Express

Un proxy inverso como Nginx o Caddy recibe la conexión y la reenvía a Node.js. En Render lo hace el balanceador. Express necesita identificar la IP del cliente y el protocolo original para limitar intentos y emitir cookies Secure. Se usaría app.set('trust proxy', 1) solo al verificar que todas las rutas tienen un salto confiable y que este sanea X-Forwarded-For y X-Forwarded-Proto. Con rutas distintas se confiaría en las IP o subredes confirmadas del proxy. [18, 19]

6. ¿Quién reinicia Node.js?

En un VPS, PM2 relanza procesos Node.js y systemd puede iniciar el servicio al arrancar Linux y reiniciarlo si falla. Un contenedor requiere una política de reinicio o un orquestador. En Render, la plataforma vigilaría GET /health y reiniciaría la instancia activa tras 60 s de fallos consecutivos. [20, 21]

Despliegue y verificación

7. Del cambio aprobado a producción

La integración continua (CI) valida cambios. El despliegue continuo (CD) publica los que pasan las pruebas. [22, 24]

  1. Validar. Con Node.js LTS fijado, GitHub Actions validaría cada propuesta y envío a main con npm ci con el package-lock.json versionado, npm test (sesiones, permisos y cifrado) y npm audit --audit-level=high. Un fallo o un hallazgo alto o crítico bloquearía el despliegue. [22, 23]
  2. Publicar. Tras revisar y fusionar en main, solo si las tres verificaciones pasan, Actions invocaría el deploy hook de Render con el SHA aprobado en ref. Su URL se guardaría como secreto en GitHub. El despliegue directo por envío quedaría desactivado. [24]
  3. Habilitar tráfico. Render comprobaría /health antes de servir la nueva versión. Si falla el arranque, mantendría la anterior. [21, 24]

8. Base gestionada y protección de la conexión

Render y Koyeb ofrecen PostgreSQL relacional. Atlas gestiona documentos. El cliente de MongoDB verificaría el certificado TLS y el nombre del servidor. Atlas aceptaría solo los rangos de salida de Render. Al ser compartidos por región, también se exigiría una credencial robusta y exclusiva. [3, 7, 12, 25, 26]

La aplicación recibiría permisos por colección. Por ejemplo, en la bitácora solo podría insertar eventos. La administración del clúster usaría otra identidad. [13, 26]

10. Comprobaciones posteriores al despliegue

Herramientas. ZAP Baseline recorrería la URL propia con reglas pasivas. Security Headers calificaría HSTS y CSP (meta global, A o superior). SSL Labs evaluaría el certificado y los protocolos TLS. npm audit identificaría dependencias con avisos conocidos. Se archivarían los informes con fecha y SHA. [23, 28, 29, 30]

Acceso del docente. Probar redirección HTTPS, /health sin datos internos, notas ajenas inaccesibles (403/404), rechazo de inyección y límite de intentos de acceso (429). Revisar cuotas y probar la URL tras el reposo. Si Atlas se pausó tras 30 días sin conexiones, reanudarlo. Entregar la URL y las credenciales de usuario y administrador por canal privado. [3, 13, 27]
